## 1. The anti-clutter thesis

Six features, added naively, would litter the screen with buttons. Instead
they collapse onto **three consistent conventions**, so the surface area a user
must learn barely grows:

1. **One home for per-program actions.** The new ⋮ menu (item 3) is the single
   place for Download / Rename / Archive on a program. Nothing else per-program
   floats loose in the left panel.
2. **One pattern for per-document download.** Every document already opens with
   a teal 📄 button; download is a small ⬇ icon *paired next to it* — same
   place, same shape, everywhere. No new rows, no new panels.
3. **One hero action per tab.** Each middle-panel tab has exactly one obvious
   primary action: Overview → **Download program package**; Corpus (unfrozen) →
   **Discover sources**; Purpose → the **status header**. Everything else is
   secondary and visually quieter.

If a proposed control doesn't fit one of these three slots, it doesn't ship in
v1.1.

## 2. Feature-by-feature design

### 2.1 Purpose tab — status header (item 4)

**Why first:** it's the cheapest, highest-clarity change, and it directly cures
the recurring "did it actually ratify?" surprise that has twice hidden tabs.

At the very top of the Purpose tab, a compact **status card**:

```
┌───────────────────────────────────────────────────────────┐
│  Purpose Statement                        ● RATIFIED       │
│  "Map the current federal commercial-lending subsidy…"     │
│  refactor mode · ratified by Mike Hsu · 2026-07-22         │
│  [ 📄 Open full statement ]   [ ⬇ ]                         │
└───────────────────────────────────────────────────────────┘
```

- The badge reads **RATIFIED** (green) or **AWAITING RATIFICATION** (amber),
  driven by `purpose_statement.json.status`. When awaiting, the card shows the
  blocking open items inline, so the path to ratification is visible.
- The interview/synthesis flow stays below the card, unchanged.
- This makes ratification state impossible to miss — the fix for the
  un-ratify class of bug is now also *visible*, not just guarded server-side.

### 2.2 Corpus tab — source-discovery agent + mini-interview (item 1)

The engine is already built (`spec/53`): catalog-anchored + model-expanded
candidates, verified against the live catalog, into a review queue where the
user **approves some / rejects some / adds their own**. v1.1 adds the
**clarifying mini-interview** — kept *optional and collapsible* per decision.

Discover panel, in order:

```
Discover sources
  [ topic / keywords ______________________ ]   [ 🔎 Discover ]
  ▸ Sharpen with a few questions (optional)      ← collapsed by default
```

Expanding "Sharpen…" runs a 3-question mini-interview generated from the
ratified Purpose Statement — e.g. "Which agencies are in scope vs. boundary?",
"Statutes and regs only, or binding guidance too?", "Include proposed/pending
rules as 'not yet law'?". The answers are folded into the discovery prompt as
extra context, tightening recall/precision. Skipping it runs discovery on the
keyword box alone — no forced friction.

Governance unchanged: discovery **proposes**, the human **accepts** into the
unfrozen manifest. The mini-interview only sharpens the proposal; it never
adds a source on its own. The Q&A exchange is captured (see §2.5) so the
census reasoning is part of the record.

### 2.3 Downloads — per-document, per-tab, and the program package (item 2)

Three tiers, all reusing the three conventions:

**(a) Per-document ⬇.** Next to each 📄 Open button (Derived Blueprint,
Crosswalk, Target Blueprint, the summaries) a small ⬇ downloads that rendered
document (HTML; PDF optional later). Same affordance everywhere.

**(b) Per-tab content ⬇.** Each tab can export its primary artifact in a
sensible format — Corpus → manifest as JSON *and* CSV; Overview → decision log
as JSON/CSV; Refactor/Redesign → the operations/dispositions table. One small
⬇ in the tab's header row, not per-item.

**(c) Program package (the hero).** On Overview, one prominent
**Download program package** button produces a single organized `.zip`:

```
<program-id>-package/
  index.html                     ← readable cover: what this is, how to navigate
  00-overview/decision-log.json  ← the append-only accountability record
  00-overview/decision-log.csv
  01-purpose/purpose-statement.json + .html
  02-corpus/manifest.json + manifest.csv
  02-corpus/corpus-texts/…       ← acquired source texts (governed)
  03-derived-blueprint/derived-blueprint.html + extractions/ + defects.json
  04-refactor/  (or 04-redesign/) operations, dispositions, invariants
  05-target/target-blueprint.html + .json
  06-align/crosswalk.html + deviation-register.json
  restricted/                    ← transcripts, CLEARLY MARKED (see §2.5)
  MANIFEST.txt                   ← file inventory + content hashes
```

The package is the deliverable a colleague opens *without the app*. It is
built by a new `GET /api/programs/{pid}/package` endpoint that assembles from
existing governed artifacts and the render endpoints — no new source of truth.

### 2.4 Left panel — per-program ⋮ menu (item 3)

Each program row gets a vertical ⋮ at its right edge. Clicking opens a small
menu:

```
government-sponsored-lending      ⋮
                                  ├ ⬇ Download package
                                  ├ ✎ Rename…
                                  └ 🗄 Archive…
```

- **Download package** — same zip as the Overview hero (one implementation,
  two entry points).
- **Rename** — opens an inline field. Safe rename is non-trivial (the
  `program_id` appears in the folder name, in `governed/*` artifacts, and in
  `runs/stamps.jsonl`). The endpoint will: validate the new slug is unique →
  move the directory → rewrite `program_id` in the purpose statement, manifest,
  and mandate → repoint stamps by **exact-match** on `program_id` (never
  substring — the lesson from the `-p2` rename). Decision-log entries are
  append-only and are not rewritten; a rename event is itself logged.
- **Archive** (our "delete", per decision) — moves `programs/<id>` →
  `programs/_archive/<id>`, with a confirm dialog. Archived programs drop out
  of the main list (the list endpoint filters `_archive/`), and an "Archived"
  affordance can restore them. **Nothing is hard-deleted**; the append-only
  decision log always survives. A true permanent-delete, if ever wanted, is a
  separate, heavily-confirmed action — out of scope for v1.1.

The ⋮ menu is the single reason clutter doesn't grow: three per-program powers,
one unobtrusive control.

### 2.5 Chat logs in the package (item 5)

Two transcripts matter: the **Purpose interview** (Phase 0) and, if used, the
**discovery mini-interview** Q&A (Phase 1 census reasoning). Both are written to
the program's `restricted/` store under ADR-016.

Per decision, the **owner's program package includes them**, in a
clearly-labelled `restricted/` subfolder with a short README explaining they are
sensitive working material. This is the owner exporting *their own* record.

Crucially, this stays distinct from **sharing**: `package-share.sh` and any
"share with colleagues" path continue to **exclude** `restricted/` entirely. So
there are two exports with two rules — *download my full record* (includes
transcripts) vs *share with others* (strips them). The UI labels which is which
so the distinction is never ambiguous.

## 3. What this adds to the screen (clutter budget)

| Surface | New controls | Net clutter |
|---|---|---|
| Left panel | one ⋮ per program (menu hidden until clicked) | +1 quiet icon/row |
| Purpose tab | one status card at top | replaces ambiguity; net clearer |
| Corpus tab | one collapsible "Sharpen…" link (discovery already present) | +1 link |
| Every doc | one ⬇ paired with existing 📄 | +1 icon, familiar pattern |
| Each tab header | one ⬇ export | +1 icon |
| Overview | one hero "Download program package" | +1 button |

No feature introduces a new panel, a new modal-heavy flow, or a second place to
do the same thing. That is the design succeeding.

## 4. Build sequencing (once approved and the bridge is back)

Ordered by risk and dependency, low-risk clarity first:

1. **Purpose status header** (§2.1) — small, pure UI, cures a real confusion.
2. **Per-document + per-tab ⬇** (§2.3a/b) — reuses render endpoints; low risk.
3. **⋮ menu shell + Archive** (§2.4) — archive is a safe move; no data loss.
4. **Program package endpoint + button** (§2.3c, §2.5) — the substantive build;
   composes everything above.
5. **Rename** (§2.4) — last of the ⋮ items; needs the exact-match stamp
   repointing and a small test harness to prove no `-p2`-style bleed.
6. **Discovery mini-interview** (§2.2) — sits on the already-built discovery
   engine; ships once that engine is on the machine.

Each lands with tests and a browser smoke check, as prior milestones did.
